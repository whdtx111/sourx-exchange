# SourX Exchange 算力交易平台开发方案

文档状态：设计基线（从零开始）  
适用仓库：`sourx-exchange`  
目标读者：产品、后端、前端、Agent、基础设施、支付与风控开发者

## 1. 结论摘要

推荐采用 **方案一：模块化单体控制面 + 卖家节点 Agent + 反向安全隧道 + 整卡租赁**，先用 Docker Compose 交付 MVP，再保留迁移到 Kubernetes 的边界。

这里的“算力传输”不是把 GPU 从卖家电脑搬到买家机器，而是：

1. 卖家在自己的设备上安装并启动 Agent。
2. Agent 通过出站 mTLS/QUIC 连接平台，报告 GPU、驱动、可用时段和健康状态。
3. 买家创建订单后，平台把一个有时间限制的工作区、端口或任务分配给这台设备。
4. 买家的容器/任务在卖家机器上运行，结果通过平台对象存储或受控隧道返回。
5. 平台根据可验证的租赁时间和心跳计量费用，订单结束、确认或争议期结束后结算给卖家。

MVP 应只承诺 **一笔订单独占一张 GPU**。消费级 GPU 的显存隔离、驱动隔离和跨平台容器隔离很难达到云厂商级别；在没有做强隔离验证前，不应宣传“多租户安全共享同一张卡”。

成功率的定义：在下文假设成立、支付渠道可用、首批设备限定为受支持的 Linux/NVIDIA 组合时，按验收标准完成可上线 MVP 的概率，而不是收入或市场成功率。推荐方案的 MVP 交付成功率估计为 **80%--85%**；要做到开放个人设备、跨平台、强隔离和大规模稳定运营，整体成功率应按 **60%--70%** 评估。

## 2. 需求边界与关键判断

### 2.1 角色

- **买家**：浏览设备和价格，提交工作负载，使用远程工作区，确认订单或发起争议。
- **卖家**：完成实名认证和收款设置，安装 Agent，发布设备，接受订单并获得结算。
- **平台运营**：审核设备、处理违规和争议、配置费率、冻结或释放订单款项。
- **平台系统**：调度、隧道、计量、支付、审计和告警，不能依赖人工改变订单金额。

### 2.2 MVP 必须支持

- 账户、实名认证/基础 KYC、角色和权限。
- 卖家设备注册、一次性安装码、设备心跳、GPU/驱动/显存/温度/网络信息。
- 设备上架、按 GPU 小时或分钟定价、押金/最低计费时长、可用时段。
- 买家下单、预授权/冻结、分配设备、启动工作区、结束订单、自动结算。
- 一个订单一个租赁工作区；首期支持 Linux + NVIDIA Container Toolkit + Docker。
- 买家通过浏览器终端/Jupyter/SSH 其中一种入口访问工作区，并能够上传、下载任务数据。
- 运行时间、心跳、故障时间、重连、取消和退款的可审计记录。
- 平台管理台：设备审核、订单检索、人工暂停、争议处理、结算对账。

### 2.3 明确不放入首个 MVP

- 同一 GPU 的安全多租户切分、MIG/vGPU 的统一适配。
- 任意操作系统和任意 GPU 厂商的“即装即用”。
- 允许买家访问卖家主机、局域网或宿主机文件系统。
- 无限时长包月、复杂竞价、链上资产或自发行平台币。
- 平台自行沉淀客户资金。平台应使用有资质的支付/托管/分账渠道，并由法务确认业务资质、税务、发票和数据合规。

### 2.4 与 AutoDL 等云算力平台的定位差异

以 [AutoDL 公开首页](https://www.autodl.com/)（访问日期：2026-10-24）为参考，其核心优势是标准化资源池、统一镜像和实例管理、按小时租用、会员价格体系以及大规模 GPU/MLU/Ascend 供给。SourX 不应在第一阶段直接复制这种重资产云平台，而应解决另一类供给问题：让个人 PC、小型工作室和闲置 GPU 服务器也能安全、透明地参与交易。

SourX 的可验证差异化应是：

- **供给更分散**：支持经过审核的个人设备和小型机房，覆盖云厂商没有的本地型号、短时闲置资源和小众区域。
- **价格更接近市场**：卖家自主定价，平台提供基准测试、故障率、在线率和历史成交数据，买家可以按价格、显存、延迟和信誉筛选。
- **交易双方都有保障**：预授权/托管、按心跳计量、争议证据和自动分账同时保护买家与卖家，而不是只提供一台实例。
- **工作负载更灵活**：首期提供可审计的工作区，后续可扩展到批任务、推理 API 和点对点数据通道；资源协议与订单核心解耦。
- **本地化和低延迟**：买家可选择距离数据源更近的节点，减少大数据集上传和跨地域带宽成本。

这些优势不能靠营销文案单独成立，必须由可公开验证的指标支撑：节点在线率、订单成功率、故障退款耗时、基准测试可重复性、平均启动时间、买家有效成本和卖家结算周期。若后续无法获得足够的个人设备供给，平台应保留接入机构节点和云 GPU 的 `ResourceProvider` 接口，以免市场两端只有一侧增长。

## 3. 业务闭环

### 3.1 卖家发布设备

1. 卖家注册、完成 KYC 和收款账户绑定。
2. 平台生成一次性、短时有效的 enrollment code；卖家在设备上运行 Agent。
3. Agent 生成设备密钥，通过出站连接完成注册，不要求平台主动连接家庭路由器。
4. Agent 上报硬件指纹、GPU UUID 的脱敏值、驱动/CUDA、显存、磁盘、带宽和区域；平台运行基准任务并记录结果。
5. 卖家选择整卡独占、价格、最短租期、可服务时段和重启策略，提交审核。
6. 审核通过后 Listing 才能被买家看到；设备不健康或心跳超时自动下架。

### 3.2 买家租用设备

1. 买家筛选 GPU 型号、显存、CUDA、区域、价格、可用性、基准分和网络质量。
2. 创建订单时锁定价格、订单时长、服务费、故障赔付上限和取消规则。
3. 支付渠道完成预授权/冻结，平台写入 `PaymentIntent` 和不可变的账本事件。
4. 调度器选择符合约束的设备，向 Agent 发送 `prepare_lease`。
5. Agent 拉取已审核的工作负载镜像，创建受限容器并返回 ready；平台签发短期 session token。
6. 买家使用受控入口连接工作区。平台每 15--30 秒记录心跳和计量读数，超时进入故障处理。
7. 服务结束时，平台停止容器、回收隧道、生成账单摘要。买家确认或自动确认窗口结束后，支付渠道向卖家分账；争议订单暂停结算。

### 3.3 争议和故障

- Agent 丢心跳：进入 `suspected_failure`，保留短暂重连窗口；超过阈值只计费到最后一次可验证心跳。
- 卖家主动停止：自动结束或迁移订单，按故障时长退款并记录卖家信誉扣分。
- 买家主动取消：按已使用时长和取消时间执行规则，不能通过客户端直接修改账单。
- 争议：冻结未结算款项，平台根据心跳、容器事件、网络探针、买家日志和快照处理。
- 多次异常：设备进入 `quarantined`，必须人工复核后才能重新上架。

## 4. 三种开发方案

### 方案一：模块化单体 + Agent + 反向隧道（推荐）

**适用目标**：先验证交易闭环，支持几十到几百台异构个人设备，要求 3--5 人团队在 12--16 周内交付可运营 MVP。

**建议组成**：

- Web：Next.js/React，买家市场、工作区、订单和卖家控制台。
- API：NestJS 或 Go 的模块化单体；按域拆分 `identity`、`catalog`、`scheduling`、`lease`、`metering`、`payment`、`dispute`、`admin`，初期共用一个部署单元和数据库。
- Agent：Go，Linux 首发；负责注册、心跳、硬件探测、Docker/NVIDIA runtime、工作区生命周期和隧道。
- 数据：PostgreSQL（事务、账本和审计）、Redis（短期锁和在线状态）、S3 兼容对象存储（镜像/数据/日志）。
- 通信：Agent 只发起出站 mTLS 长连接；控制指令带序列号、过期时间和幂等键。买家工作区通过 gateway 转发，避免开放卖家入站端口。
- 部署：开发和小规模生产用 Docker Compose；网关、API、worker、数据库可独立扩容。
- GPU：整卡独占；使用经签名的基础镜像、非 root 用户、seccomp/AppArmor、无宿主目录挂载、资源上限和网络白名单。

**优点**：交付快、故障面少、容易端到端调试；后续可以把 scheduler、metering、payment worker 单独拆出。  
**缺点**：单体需要严格模块边界；跨地域调度、强隔离和超大规模会在后期重构。  
**估计**：12--16 周 MVP，3--5 名工程师；MVP 交付成功率 **80%--85%**，上线后大规模开放成功率 **60%--70%**。

### 方案二：Kubernetes 云原生调度平台

**适用目标**：从一开始就面向机构机房、云 GPU 和较大规模资源池，期望数千节点、批处理队列、容器编排和多地域调度。

**建议组成**：

- 控制面拆为 API、订单、支付、调度、节点、计量、通知和争议服务。
- Kubernetes + NVIDIA GPU Operator；批处理使用 Volcano/Kueue，服务型工作区使用自定义 Lease Operator。
- Agent 作为 DaemonSet 或独立节点服务；边缘个人设备通过 gateway 注册，受控节点通过 Kubernetes 注册。
- Kafka/NATS 传递事件，PostgreSQL 按服务拆库或按领域分 schema，Prometheus/Grafana/Loki/Tempo 做可观测性。
- 网络使用 WireGuard/私有 overlay；权限用短期 SPIFFE/SPIRE 身份或等价 mTLS 体系。

**优点**：资源编排、自动扩缩、配额、批任务和机构客户能力强；长期平台边界清晰。  
**缺点**：组件多、运维门槛高；个人设备接入、支付状态和争议处理仍需额外开发，不能因为上了 K8s 就解决信任问题。  
**估计**：20--32 周首个可运营版本，6--10 名工程师；按期交付成功率 **65%--75%**，成熟后的规模化成功率 **75%--85%**。不建议在没有业务验证前直接采用。

### 方案三：P2P/边缘优先的去中心化市场

**适用目标**：希望平台只做发现、撮合和协议中继，买卖双方尽量直连，面向全球家庭设备或极端低平台基础设施成本。

**建议组成**：

- Agent 使用 libp2p/WebRTC/QUIC，通过 rendezvous 服务发现，尽量建立买家到卖家的直连，失败时经中继。
- 订单和租约采用签名凭证；平台服务保存撮合、风控和争议证据。
- 支付仍优先接入合规的法币托管/分账；链上合约只有在目标市场、税务、退款和稳定币合规明确后才评估。
- 每个工作区使用一次性 capability token，平台只转发握手和计量证明，不把平台主密钥交给买家。

**优点**：跨地域延迟和中继带宽成本可能更低；平台故障对已建立会话的影响较小。  
**缺点**：NAT/CGNAT、家庭网络、端到端审计、恶意节点、断线续租和退款极难统一；直连会放大买卖双方的网络与隐私风险。  
**估计**：24--40 周，7--12 名工程师；按期交付成功率 **45%--60%**。适合作为方案一验证后的实验方向，不适合作为第一版主路线。

### 4.1 对比表

| 维度 | 方案一：模块化单体 | 方案二：Kubernetes | 方案三：P2P 边缘 |
| --- | --- | --- | --- |
| MVP 速度 | 快，12--16 周 | 中，20--32 周 | 慢，24--40 周 |
| 初期成本 | 低到中 | 高 | 中，研发成本高 |
| 个人 PC 接入 | 好，统一由 Agent 出站连接 | 中，需要额外边缘层 | 理论好，实际受 NAT 影响 |
| 隔离能力 | 整卡独占可控 | 最强，但配置复杂 | 取决于节点，最难证明 |
| 调度与批任务 | 足够 MVP | 最强 | 复杂 |
| 支付/争议可审计 | 强，统一控制面 | 强，但服务间一致性难 | 中，证据和状态同步难 |
| 扩展到千节点 | 需要拆服务 | 好 | 不确定 |
| 推荐度 | **首选** | 第二阶段 | 研究/实验 |

## 5. 推荐方案的技术基线

### 5.1 仓库结构建议

```text
apps/
  web/                  # 买家市场、卖家控制台、管理台
  api/                  # 模块化控制面
  worker/               # 调度、计量、结算、通知异步任务
agent/
  cmd/sourx-agent/
  internal/hardware/
  internal/runtime/
  internal/tunnel/
  internal/controlplane/
packages/
  contracts/            # OpenAPI、事件 schema、状态常量
  ui/
infra/
  compose/
  migrations/
  observability/
docs/
  adr/
  runbooks/
```

如果团队最终统一使用 Go 或 TypeScript，可合并 API 和 worker，但 `agent` 与平台控制面的协议仍应通过版本化 schema 隔离。

### 5.2 核心领域对象

- `User`：账户、角色、KYC 状态、风控状态。
- `ProviderProfile`：卖家收款账户、服务条款、信誉和累计结算。
- `Node`：设备身份、Agent 版本、区域、网络、状态、最后心跳。
- `GpuResource`：型号、显存、驱动、CUDA、基准结果、独占策略。
- `Listing`：价格、最短时长、可用窗口、镜像能力、押金和上架状态。
- `Order`：买家、Listing 快照、价格快照、时长、费用拆分、状态和取消规则。
- `Lease`：具体 Node/GPU 分配、租约 token、开始/结束时间、故障时间。
- `Workspace`：容器、端口、镜像 digest、资源限制、清理状态。
- `MeterReading`：单调时间戳、心跳、GPU 利用率、故障标志、签名/校验值。
- `PaymentIntent`、`LedgerEntry`、`Payout`：支付状态、平台服务费、卖家应收、退款、对账号。
- `Dispute`：原因、证据、冻结金额、处理决定和操作人。
- `AuditLog`：谁在何时以什么理由改变了什么字段；追加写入，禁止覆盖。

金额全部使用最小货币单位整数，禁止浮点数；每个支付和结算请求必须带幂等键。

### 5.3 状态机和不变量

**Node**：`pending_enrollment -> online -> draining -> offline`；风险设备可转 `quarantined`。  
**Listing**：`draft -> pending_review -> published -> paused -> retired`。  
**Order**：`created -> payment_pending -> paid -> allocating -> active -> ending -> completed`，另有 `cancelled`、`failed`、`disputed`、`refunded` 分支。  
**Payment**：`created -> authorized -> captured/partially_refunded -> settled`，失败、全部退款和争议冻结必须可追溯。

必须保证：

1. 一个 GPU 在任意时间最多绑定一个 active lease。
2. 没有有效支付授权，不能启动可计费工作区。
3. 没有有效租约 token，Agent 不执行买家命令。
4. 每个计费区间最多入账一次；重试只能重复读取或产生同一幂等结果。
5. 争议、风控冻结或支付 webhook 未确认时，不释放卖家应收。
6. 订单结束一定触发容器清理和 token 失效；清理失败会进入告警和人工队列。

### 5.4 Agent 与控制面接口示例

- `POST /api/v1/agent/enroll`：一次性 enrollment code 换取设备身份和证书。
- `POST /api/v1/agent/heartbeat`：状态、能力、资源和 Agent 版本；服务端校验时间窗和 nonce。
- `POST /api/v1/agent/inventory`：GPU、驱动、容器 runtime、磁盘和带宽探测结果。
- `GET /api/v1/agent/commands/stream`：出站长连接拉取命令；命令包括 prepare/start/stop/collect。
- `POST /api/v1/agent/commands/{id}/ack`：成功、失败、日志摘要和重试建议。
- `POST /api/v1/orders`：买家创建订单，服务端重新计算金额。
- `POST /api/v1/orders/{id}/pay`：创建支付意图，不接受客户端传入最终金额。
- `POST /api/v1/orders/{id}/lease`：查询工作区、入口和短期 session token。
- `POST /api/v1/orders/{id}/finish`：买家申请结束；平台仍需由服务端核算计量。
- `POST /api/v1/payments/webhooks/{provider}`：验签、去重、记录原始事件和处理结果。
- `POST /api/v1/disputes`：创建争议并冻结对应结算批次。

API 必须有 OpenAPI 文档、版本前缀、统一错误码、请求追踪 ID、权限矩阵和速率限制。外部 webhook 只能通过签名验证后的事件驱动状态变更。

### 5.5 工作区和网络安全

- Agent 只允许出站连接；不要要求卖家开放 SSH、路由器端口或上传平台长期密钥。
- 工作区使用平台签名的镜像 digest；禁止买家提交任意宿主机挂载和 `--privileged`。
- 容器使用非 root、只读根文件系统、最小 capability、CPU/内存/PID/磁盘上限；必要时加入 gVisor/Kata，但先验证 NVIDIA 兼容性。
- 工作区默认无内网访问，仅允许对象存储、镜像仓库和任务所需地址；买家与卖家都使用短期、最小权限 token。
- 记录命令审计、镜像 digest、端口、资源变化、心跳、温度和异常退出原因；日志脱敏，避免把 API key、支付信息写入日志。
- 卖家主机不应把平台服务与个人文件混装；安装器需要明确数据目录、卸载方式、升级签名和紧急停机按钮。

## 6. 计费、托管和结算设计

### 6.1 费用模型

订单金额 = `GPU 单价 × 可计费分钟/60 + 存储/带宽费用 + 平台服务费 + 可选押金`。  
首期只做整卡时长费，存储和带宽采用明确上限，避免第一版出现无法解释的账单。

计费以服务端单调时间、Agent 心跳和工作区状态交叉验证。时钟漂移、断线重连和暂停必须写入计量事件，不能使用客户端时间直接计费。

### 6.2 托管和分账

- 支付层使用支持预授权、冻结、分账、退款和 webhook 的合规渠道。
- 平台只保存支付意图、渠道交易号和内部账本，不保存银行卡敏感数据。
- 预授权成功不等于立即给卖家结算；订单结束后先进入 `settlement_pending`，经过自动确认窗口和风控检查再分账。
- 结算金额 = 已确认可计费金额 - 平台费 - 退款/赔付 - 税费/渠道费（按业务法务确认）。
- 对账任务每日运行：支付渠道流水、内部账本、卖家应收三方必须能按订单号互相定位。

### 6.3 争议规则首版建议

- 买家在订单结束后 24 小时内发起争议；存在争议则冻结全部未结算金额。
- 平台只按证据决定“服务不可用分钟数”，不可用分钟自动退款；买家输入无法证明的损失不直接从卖家余额扣除。
- 卖家设备无心跳超过 2 个计费周期，后续时间不计费；频繁故障触发保证金/信誉规则。
- 争议处理必须产生可导出的决定记录，包含证据摘要、规则版本、操作人和时间。

## 7. 分阶段交付与验收

### 阶段 0：一周内冻结的决策

- 首发区域、支付渠道、KYC/税务边界、支持的 OS/GPU/驱动矩阵。
- 只支持整卡独占还是同时支持 CPU；首版建议整卡 NVIDIA GPU。
- 买家入口选浏览器终端、Jupyter 或 SSH 之一；首版建议浏览器终端 + Jupyter 二选一。
- 订单取消、故障退款、争议时限、平台服务费和最低计费时长。

### 阶段 1：设备和目录（第 2--4 周）

- 账户、角色、设备注册、心跳、硬件探测、Listing 审核。
- 验收：支持设备离线/恢复、重复注册、证书吊销、版本不兼容拦截；运营台能看到最近心跳和原始探测摘要。

### 阶段 2：租约和工作区（第 5--8 周）

- 订单状态机、调度锁、Agent 命令流、工作区启动/停止、受控入口和日志。
- 验收：同一 GPU 不能双租；断线能正确停止或进入故障；订单结束后容器、token、端口全部回收。

### 阶段 3：支付、计量和结算（第 9--11 周）

- 支付沙箱、预授权/冻结、计量 worker、账本、退款、分账 webhook、对账。
- 验收：重复 webhook 不重复入账；重试不会重复收费；模拟宕机、断网、取消、争议后账单与余额仍可重建。

### 阶段 4：风控和上线前验证（第 12--16 周）

- 镜像签名、限流、告警、人工审核、设备封禁、数据备份、灾备演练和运行手册。
- 验收：至少 20 台测试节点、100 个并发租约创建请求、连续 72 小时心跳测试；核心指标和告警可被值班人员定位。

### MVP 验收指标

- 设备心跳在线状态延迟 P95 < 60 秒。
- 订单到工作区 ready 的 P95 < 5 分钟（镜像已缓存时）。
- 计量重复记账率为 0；支付 webhook 幂等测试 100% 通过。
- 模拟 Agent 断线时，最多多计费 1 个计量周期，且可自动退款。
- 所有订单、支付、计量、争议事件都有审计记录和追踪 ID。
- 高危容器能力（特权、宿主挂载、任意内网访问）在自动化测试中被拒绝。

## 8. 主要风险和处理顺序

1. **网络可达性**：家庭宽带、CGNAT 和动态 IP。先采用 Agent 出站长连接和平台网关，后续再尝试直连优化。
2. **GPU/驱动差异**：锁定支持矩阵，注册时做基准和兼容性检查；不符合矩阵的设备不能上架。
3. **隔离不足**：整卡独占、容器最小权限、无宿主挂载；通过安全评审前不开放任意镜像和任意端口。
4. **支付合规**：支付/托管/分账和税务是上线门槛，不应把“数据库余额”当作合法托管资金。
5. **恶意买家任务**：镜像白名单、资源限制、网络出口策略、滥用举报、人工封禁和审计；仍需准备安全事件响应流程。
6. **卖家服务不稳定**：在线信誉、基准分、故障赔付、自动下架和争议证据共同处理，不能只依赖评分。
7. **账单争议**：金额快照、单调计时、事件账本、规则版本和可重放对账必须在支付接入前完成。

## 9. 后续 Agent 的实现顺序

后续开发应按以下顺序提交，每一步都保持可运行：

1. 写入 `packages/contracts`：枚举、状态机、OpenAPI 和事件 schema。
2. 实现数据库迁移与订单/租约/支付不变量测试，再实现页面。
3. 实现 Agent 的注册、心跳和 inventory，不先做任意远程 shell。
4. 实现单节点、单 GPU、单订单的 happy path，再补断线、取消、重试和清理。
5. 接入支付沙箱和 webhook 幂等，使用可重放的模拟事件测试账本。
6. 加入管理员审核、争议、审计和告警后，才扩大设备矩阵或引入 Kubernetes。

任何新功能都要回答四个问题：谁授权、运行在哪台机器、如何计量、失败后如何退款或清理。不能回答清楚时，不应进入生产订单路径。

## 10. 推荐决定

现在选择 **方案一**。理由是：

- 它首先解决真正的核心风险：个人设备连接、工作区隔离、租约状态、计量和托管结算，而不是先投入复杂编排平台。
- 模块化边界和版本化协议足以让后续 Agent 并行开发；调度、计量和支付可以在有负载后独立拆分。
- 整卡独占降低 GPU 虚拟化和争议复杂度，能更快获得真实设备、真实订单和真实故障数据。
- 反向隧道适配家庭网络，平台不会要求卖家暴露入站端口；这对个人 PC 是上线的必要条件。
- 方案一完成后，方案二的 K8s 执行器可以作为第二种 `ResourceProvider` 接入，方案三的直连隧道也可以作为网关优化，而不需要重写订单和支付核心。

本推荐成立的前提是：首发范围受控、支付合规由专业渠道承担、首期只支持已验证的 Linux/NVIDIA 设备，并接受整卡独占和有限的买家工作负载。若产品一开始就要求全球开放、任意硬件、强多租户隔离和大规模批处理，应直接重新评估方案二，并把 MVP 周期和成功率下调。
