# SourX Exchange 第一版详细开发计划

文档状态：开发前计划，暂不编码  
对应架构：[算力交易平台开发方案](算力交易平台开发方案.md) 的方案一  
首版目标：完成可审计的“买家付费 -> 租约启动 -> 受限算力任务 -> 计量 -> 结束/退款/结算”闭环

## 1. 开发原则

### 1.1 首版产品边界

首版只支持：

- Linux + NVIDIA GPU + Docker/NVIDIA Container Toolkit。
- 一笔订单独占一张 GPU，不做同卡多租户切分。
- 买家提交受限任务并取得结果，不提供卖家主机访问权。
- 卖家 Agent 只主动连接平台，不要求家庭路由器开放入站端口。
- 使用支付渠道的预授权/冻结、退款和分账能力；平台不把数据库余额当作资金托管。
- 平台先支持一个支付渠道、一个区域和一套镜像白名单，验证闭环后再扩展。

首版明确不做：任意 Docker 镜像、任意 SSH、宿主机目录挂载、Docker socket、特权容器、同 GPU 共享、跨 GPU 迁移、包月套餐和链上结算。

### 1.1.1 必须公开的信任边界

平台能够限制买家访问卖家主机，但普通消费级 GPU 和卖家自有操作系统不提供机密计算保证。拥有主机 root 权限的卖家理论上可以观察运行中的进程、网络元数据或 GPU 内存，因此第一版：

- 不宣称“卖家无法看到买家任务数据”或“机密 GPU 计算”。
- 在订单页、卖家协议和安全文档中明确该风险；敏感数据买家应选择经过更高等级审核的机构节点。
- 通过节点 KYC、信誉、设备审计、最小数据保留和异常举报降低风险，但不能把这些措施描述成密码学隔离。
- 将可信执行环境、机密虚拟机和硬件级 GPU 内存保护列为后续专项，不阻塞首版交易闭环。

### 1.2 买家获得的权利

买家获得的是 **指定租约有效期内、指定 GPU 上运行已授权任务的能力**，不是卖家设备的控制权，也不是卖家工作区或磁盘的访问权。

所有买家请求都必须同时满足：

1. 请求者是订单买家。
2. 订单和租约处于允许状态。
3. capability token 未过期、未撤销且 scope 匹配。
4. 请求指向该订单的 sandbox/job/artifact，不能指向 Node、宿主机或其他订单。
5. 服务端根据订单状态重新校验，不信任浏览器传入的价格、设备、GPU 或路径。

### 1.3 交付原则

- 先写契约、状态机和不变量，再实现页面和运行时。
- 每个阶段都必须有可运行的垂直切片和负向安全测试。
- 任何异步命令、支付 webhook、计量事件都必须幂等。
- 不把“Agent 能执行命令”设计成公开 API；Agent 只执行平台签名的、白名单内的命令。
- 所有时间、金额、权限和清理动作都能从数据库事件和审计日志重放。

## 2. 目标架构和权限边界

### 2.1 组件

```text
买家 Web / SDK
        |
        v
API + Auth + Order + Lease + Metering + Payment + Admin
        |                  |
        |                  +--> PostgreSQL（业务、账本、审计）
        |                  +--> Redis（短锁、在线状态、限流）
        |                  +--> Object Storage（输入、输出、日志）
        v
Gateway（工作负载 API，校验短期 capability token）
        ^
        | 仅允许 Agent 出站 mTLS/QUIC 长连接
        v
卖家节点 Agent -> 受限 Sandbox Runtime -> 指定 GPU
```

### 2.2 卖家主机目录边界

Agent 安装后只使用专用目录，例如 `/var/lib/sourx-agent`，目录归 Agent 专用系统用户或最小权限服务账户所有，建议分为：

```text
/var/lib/sourx-agent/
  cache/       # 已审核镜像和可清理缓存
  runtime/     # 租约沙箱的临时元数据，不放卖家个人文件
  logs/        # Agent 自身日志，脱敏后上传
  certs/       # 设备证书，权限 0600
```

禁止把 `/home`、桌面、SSH key、浏览器目录、其他磁盘目录、Docker socket 或卖家自定义路径挂载到买家 sandbox。Agent 不扫描、不上传卖家文件名、文件内容或完整磁盘目录；只上报容量、健康和运行时所需的硬件摘要。

### 2.3 买家权限矩阵

| 资源 | 允许 | 明确禁止 | 首版实现 |
| --- | --- | --- | --- |
| 指定 GPU | 使用订单分配的 GPU 计算能力 | 访问其他 GPU、修改驱动、重置设备 | runtime 按 GPU UUID 绑定，整卡独占 |
| sandbox 文件 | 读写该订单的临时 `/workspace` | 访问卖家磁盘、其他订单、宿主机根目录 | 临时卷，订单结束销毁 |
| 输入数据 | 读取自己上传或平台授权的输入 artifact | 读取卖家文件、其他买家数据 | 对象存储短期签名 URL |
| 输出数据 | 写入自己订单的 output artifact | 写入宿主机路径或其他订单路径 | 只允许平台签发的上传 token |
| 镜像 | 使用平台审核的镜像 digest | 拉取任意镜像、修改 runtime 参数 | 镜像白名单 + digest 固定 |
| 进程 | 在容器内启动任务进程 | host PID、特权、宿主机命令、Docker API | 非 root、drop capabilities、PID/CPU/内存上限 |
| 网络 | 访问平台 Gateway、对象存储和显式允许的地址 | 卖家局域网、云元数据、任意入站连接 | 默认 deny，egress allowlist |
| 控制操作 | 提交、查询、停止自己的 job | 启停节点、查看 Agent、操作其他订单 | API scope + 所有权校验 |
| 日志/指标 | 查看自己的任务日志和摘要 | 查看卖家系统日志、其他订单指标 | 按 `order_id/job_id` 过滤 |
| 凭证 | 使用短期任务 token | 获得平台、卖家、支付或 Agent 长期密钥 | TTL、scope、audience、可撤销 |

### 2.4 首版访问模式

首版默认采用 **Job API**：买家上传任务包和输入数据，指定平台允许的镜像与入口，提交 job，轮询状态，下载输出。API 不暴露任意 shell。

如业务验证确实需要交互式开发环境，再增加 feature flag 控制的 Jupyter 模式：

- Jupyter 运行在订单专属 sandbox 内，而不是卖家主机。
- 默认关闭 Jupyter Terminal、宿主目录、任意端口转发和内网访问。
- 只能访问该订单临时卷及被授权的输入 artifact。
- session token 过期、订单结束、争议冻结或管理员封禁时立即失效。
- Jupyter 模式必须单独通过安全评审，不作为 Job API 的隐式能力。

## 3. 状态机和核心不变量

### 3.1 状态

- `Node`：`pending_enrollment -> online -> draining -> offline`；异常进入 `quarantined`。
- `Listing`：`draft -> pending_review -> published -> paused -> retired`。
- `Order`：`created -> payment_pending -> paid -> allocating -> active -> ending -> completed`；异常分支为 `cancelled`、`failed`、`disputed`、`refunded`。
- `Lease`：`requested -> reserving -> starting -> ready -> running -> stopping -> ended`；异常分支为 `start_failed`、`interrupted`、`cleanup_failed`。
- `Sandbox`：`requested -> creating -> ready -> running -> destroying -> destroyed`；任何状态都可以进入 `quarantined`，禁止继续接收买家请求。
- `Job`：`created -> queued -> running -> succeeded/failed/cancelled/expired`。
- `Payment`：`created -> authorized -> captured -> settled`；支持 `failed`、`voided`、`partially_refunded`、`disputed`。

### 3.2 必须自动化保证的不变量

1. 同一 GPU 同时最多有一个 `ready/running` lease。
2. 没有 `authorized` payment，不能创建可计费 sandbox。
3. 没有有效 lease、scope 和 owner 校验，Gateway 不转发请求。
4. Job 只能由该订单的买家创建、读取和停止。
5. 计量区间按 `(lease_id, bucket_start)` 唯一；重试不重复收费。
6. 订单结束、支付失败、租约超时或管理员封禁都会撤销 capability token。
7. sandbox 销毁前不得标记订单完成；清理失败必须进入告警和人工队列。
8. 结算前必须满足订单已结束、争议窗口规则通过、支付状态可结算、审计事件完整。

## 4. 12--16 周开发计划

计划按 8 个双周迭代组织；每个迭代包含产品、API、Agent、Web、基础设施和测试任务。若只有 3 人团队，后四个迭代可各延长一周。

### Iteration 0：项目基线与安全设计（第 1 周）

**目标**：冻结首版边界，让后续 agent 使用同一套契约开发。

任务：

- `P0-01` 确认首发区域、币种、支付渠道沙箱、KYC 供应商和法务边界。
- `P0-02` 固定 Linux/NVIDIA/驱动/Docker 支持矩阵，选择一张测试 GPU。
- `P0-03` 建立 monorepo 目录、代码规范、提交规范、环境变量清单和本地 Compose 约定。
- `P0-04` 编写 ADR：控制面技术栈、Agent 通信、sandbox runtime、对象存储、日志和 token 方案。
- `P0-05` 编写威胁模型，至少覆盖恶意买家、恶意卖家、平台账号泄漏、Agent 失联、容器逃逸和支付重复 webhook。
- `P0-06` 定义 OpenAPI、事件 schema、状态枚举、错误码、幂等键和 trace ID 规范。

交付物：

- `docs/adr/` 中的决策记录、威胁模型和数据流图。
- `packages/contracts` 的初版 schema 和状态机文档。
- 本地 PostgreSQL、Redis、对象存储模拟服务能启动；不包含业务实现。

退出条件：产品和安全负责人确认“买家没有宿主机/卖家工作区权限”的边界；所有后续任务都有明确依赖。

### Iteration 1：身份、权限和审计骨架（第 2--3 周）

**目标**：建立所有后续功能依赖的身份与授权基础。

任务：

- `P1-01` 实现用户注册、登录、刷新 token、登出和账户封禁。
- `P1-02` 实现 buyer/provider/operator 角色，服务端权限中间件和资源 owner 校验。
- `P1-03` 实现 KYC 状态占位和收款账户状态，不接真实敏感支付数据。
- `P1-04` 实现 `AuditLog` 追加写入、操作者、对象、前后摘要、规则版本和 trace ID。
- `P1-05` 实现 API 速率限制、请求体大小限制、统一错误格式和敏感字段脱敏日志。
- `P1-06` Web 完成登录、角色路由、账户状态和基础错误页。

测试：越权读取其他用户订单、伪造 role、重放 token、封禁用户调用 API、审计记录完整性。

退出条件：所有受保护 API 都经过统一认证和授权；任何 operator 操作都有审计记录。

### Iteration 2：Agent 注册、心跳和设备目录（第 3--5 周）

**目标**：卖家能安全接入一台受支持的 GPU 节点，平台能判断在线和健康状态。

任务：

- `P2-01` 实现一次性 enrollment code：短 TTL、单次消费、绑定 provider、可撤销。
- `P2-02` Agent 生成本地密钥，完成注册并获取设备证书；私钥不上传。
- `P2-03` 实现出站 mTLS/QUIC 长连接、重连退避、命令序列号、过期时间和 ack。
- `P2-04` 实现 inventory：GPU UUID 脱敏值、型号、显存、驱动、CUDA、runtime、磁盘容量摘要、网络探针。
- `P2-05` 实现 heartbeat、版本检查、证书吊销、节点 drain/quarantine。
- `P2-06` Web 完成设备列表、在线状态、硬件摘要和 Agent 安装码展示。
- `P2-07` 运营台完成节点审核、手动暂停和封禁。

安全测试：重复 enrollment、伪造 heartbeat、旧证书、命令重放、异常大 inventory、上传卖家路径和文件名。

退出条件：Agent 不能通过 API 访问其他节点；控制面能在 60 秒内发现离线；支持测试节点注册、断线、恢复和吊销。

### Iteration 3：Listing、价格和调度预留（第 5--7 周）

**目标**：卖家发布可交易资源，买家能看到经过审核的能力和价格。

任务：

- `P3-01` 实现 Listing 草稿、审核、发布、暂停、下架和版本化价格快照。
- `P3-02` 实现 GPU 能力过滤：型号、显存、CUDA、区域、基准分、可用窗口。
- `P3-03` 实现整卡独占资源锁和 reservation TTL，防止两个买家同时占用。
- `P3-04` 实现价格计算服务：GPU 时长、平台费、最低时长、押金，全部使用整数最小货币单位。
- `P3-05` Web 完成市场列表、详情、筛选、价格明细和设备信誉摘要。

测试：价格快照不可被客户端修改；并发预留同一 GPU 只有一个成功；下架后不能新建订单；节点不健康自动隐藏。

退出条件：使用模拟支付即可完成“选择 Listing -> 生成订单报价 -> 临时锁定 GPU”。

### Iteration 4：支付沙箱、订单和租约编排（第 7--9 周）

**目标**：完成下单、支付授权和租约编排，但暂不让买家执行任意任务。

任务：

- `P4-01` 实现 Order 创建、金额快照、取消规则和状态机。
- `P4-02` 接入支付 provider adapter 和沙箱预授权/冻结、撤销、退款接口。
- `P4-03` 实现 webhook 验签、事件去重、幂等处理和原始事件留存。
- `P4-04` 实现 scheduler：按能力与健康状态选节点，创建 reservation 和 lease。
- `P4-05` 实现 Agent 控制命令：`prepare_sandbox`、`start_sandbox`、`stop_sandbox`、`collect_evidence`。
- `P4-06` Web 完成订单确认、支付状态、租约准备中、取消和失败页面。

测试：支付重复回调、支付成功但 Agent 启动失败、超时取消、并发下单、服务重启恢复状态。

退出条件：支付成功后能创建唯一 lease；没有支付授权的订单不会调用 sandbox 启动命令；所有失败路径都能释放 reservation。

### Iteration 5：Sandbox Runtime 和买家权限（第 9--11 周）

**目标**：在卖家机器上创建真正受限的订单沙箱，验证买家只能使用指定 GPU 和临时卷。

任务：

- `P5-01` Agent 实现审核镜像拉取、digest 校验、缓存和清理。
- `P5-02` Agent 实现 sandbox spec，只允许平台生成的固定字段：GPU UUID、CPU/内存/PID/磁盘上限、临时卷、网络策略、镜像 digest、入口命令。
- `P5-03` 强制非 root、只读根文件系统、drop capabilities、无 privileged、无 host PID/IPC/network、无宿主挂载、无 Docker socket。
- `P5-04` 按 GPU UUID 绑定资源，验证容器不能看到其他 GPU。
- `P5-05` 实现临时卷创建、配额、订单结束销毁和销毁失败告警。
- `P5-06` 实现 capability token：`aud`、`order_id`、`lease_id`、scope、TTL、nonce、撤销版本。
- `P5-07` 编写“攻击型买家”测试：读取 `/`, `/proc`, Docker socket、宿主目录、内网、云元数据、其他订单目录并确认全部失败。

退出条件：在测试节点上可以证明买家没有卖家磁盘或主机控制权；租约结束后 token 立即失效，sandbox 和临时卷最终被清理。

### Iteration 6：Job API、Gateway 和数据生命周期（第 11--13 周）

**目标**：提供首版可用的算力任务入口，不暴露任意 shell。

任务：

- `P6-01` 定义 Job、Artifact、Input、Output schema 和状态机。
- `P6-02` 实现任务包上传、病毒/类型/大小检查、对象存储隔离前缀和短期签名 URL。
- `P6-03` 实现 Job API：创建、排队、运行、日志摘要、取消、查询和结果下载。
- `P6-04` Gateway 校验 capability token、订单 owner、job owner、路径前缀和请求大小。
- `P6-05` Agent 只从平台命令接收 job spec，禁止客户端直接传 Docker 参数。
- `P6-06` 实现网络 egress allowlist，阻断 RFC1918、localhost、云厂商 metadata 和任意入站端口。
- `P6-07` 定义数据生命周期：订单结束后输入/输出/临时卷按规则保留或删除，删除事件可审计。
- `P6-08` Web 完成任务提交、状态、日志摘要和结果下载。

退出条件：买家可以提交一项受限 GPU 任务并取得输出；不能提交任意镜像、任意挂载、任意端口或任意宿主命令。

### Iteration 7：计量、结束、退款、结算和运营台（第 13--15 周）

**目标**：让订单金额可重建，故障能正确停计费和退款。

任务：

- `P7-01` 实现 heartbeat/metering worker，按服务端时间、sandbox 状态和 Agent 证据生成计量桶。
- `P7-02` 实现断线、暂停、故障、重连和 grace period 规则；最多多计费一个计量周期。
- `P7-03` 实现订单结束编排：停止 job、撤销 token、停止 sandbox、清理卷、生成账单摘要。
- `P7-04` 实现 append-only ledger、平台费、退款、赔付、卖家应收和结算批次。
- `P7-05` 实现确认窗口、争议冻结、自动结算和支付分账 adapter。
- `P7-06` 运营台完成订单检索、节点隔离、争议证据、退款/暂停操作和审计查看。
- `P7-07` 实现每日支付渠道、内部账本、卖家应收三方对账报告。

测试：重复计量、重复 webhook、宕机恢复、手动争议、部分退款、清理失败、结算重试和对账差异。

退出条件：同一订单可以从事件重建最终账单；买家故障退款和卖家结算不会重复或丢失。

### Iteration 8：安全评审、可观测性和小规模试运行（第 15--16 周）

**目标**：在有限节点和受邀买家范围内验证真实闭环。

任务：

- `P8-01` 增加 Prometheus 指标、结构化日志、trace、告警和脱敏检查。
- `P8-02` 完成数据库备份、恢复演练、证书轮换、密钥吊销和 Agent 升级回滚。
- `P8-03` 执行容器逃逸、权限越界、网络越界、token 重放、支付重放和订单并发测试。
- `P8-04` 使用至少 5--20 台测试节点进行 72 小时心跳、租约和清理测试。
- `P8-05` 编写卖家安装、买家任务、故障处理、退款、争议和紧急下线 runbook。
- `P8-06` 仅对受邀用户开放，记录首批订单的启动时间、故障率、计量差异、清理成功率和退款耗时。

退出条件：安全负责人签署 sandbox 边界；产品负责人签署订单/退款规则；运维负责人能在无开发介入下暂停节点和处理常见故障。

## 5. 后续 Agent 的任务拆分规则

### 5.1 推荐并行工作流

后续可以按以下工作流分配给不同 agent，但必须共享 `packages/contracts`：

- **Contracts agent**：状态机、OpenAPI、事件 schema、错误码、权限 scope。
- **Control-plane agent**：身份、目录、订单、租约、支付、计量、账本、管理 API。
- **Node-agent agent**：注册、证书、心跳、inventory、sandbox runtime、清理和升级。
- **Web agent**：买家市场、订单、任务、卖家设备、管理台；不得自行绕过 API 权限。
- **QA/security agent**：不变量测试、攻击型买家测试、支付幂等、故障注入和验收报告。

若多个 agent 同时工作，必须先合并 contracts，再实现依赖它的模块；不得各自发明状态值、金额字段或 token claim。

### 5.2 每个任务的完成定义

一个任务只有满足以下条件才算完成：

1. 有对应的 schema、数据库迁移或接口文档。
2. 有成功路径和至少一个权限/失败路径测试。
3. 有幂等、超时、重试和回滚行为说明。
4. 日志不包含 token、支付敏感数据、卖家路径或输入文件内容。
5. 变更有审计事件或说明为什么不需要审计。
6. 本地 Compose 或测试节点可复现验证。
7. 更新 runbook 或验收记录，说明如何验证和如何人工止损。

## 6. 首版必须完成的安全验收

### 6.1 买家越权测试

- 改写 `order_id`、`lease_id`、`job_id`、artifact key 后返回 403/404，不泄露资源是否存在。
- 使用过期、撤销、其他订单或其他用户 token 全部失败。
- 买家无法调用 Agent、Node、管理员和支付内部 API。
- 买家无法通过 job 参数注入宿主挂载、特权、host network、host PID、Docker socket 或额外 GPU。

### 6.2 主机和网络测试

- 容器内不能访问卖家 home、Agent cert、Docker socket、宿主机根目录和其他租约卷。
- 容器不能访问卖家局域网、localhost、RFC1918、云 metadata 和未允许的出站地址。
- 订单结束后，端口、token、容器、临时卷和进程全部回收；残留会触发告警并阻止节点重新上架。

### 6.3 计费与清理测试

- 断线、进程崩溃、支付撤销、管理员封禁都会停止接收新 job 并触发清理。
- 多次重试 webhook、计量 worker 和清理 worker 不产生重复收费、重复退款或重复结算。
- 任何清理失败都有 `cleanup_failed` 状态、告警、人工重试和审计记录。

## 7. MVP 发布门槛

满足以下条件才能进入受邀试运行：

- 首发支持矩阵、支付渠道和争议规则已经书面冻结。
- 至少一个真实卖家节点通过注册、基准、下单、任务、结束和清理全流程。
- 任何买家请求都只能落到自己的订单 sandbox；安全负向测试全部通过。
- 设备心跳在线状态 P95 < 60 秒，缓存镜像时工作区 ready P95 < 5 分钟。
- 计量重复记账率为 0；支付 webhook 幂等测试 100% 通过。
- Agent 断线最多多计费一个计量周期，并能自动退款。
- 订单、支付、计量、job、sandbox、争议和清理事件均可审计和追踪。
- 运营人员能够一键暂停节点、停止订单、撤销 token、冻结结算和导出证据。

## 8. 需要在编码前确认的决策

以下问题如果没有答案，先停留在 Iteration 0，不进入业务编码：

1. 首发区域和支付渠道是否支持预授权、冻结、退款和卖家分账？
2. KYC、发票、税务和平台资金流由哪一家合规服务承担？
3. 首版 Job API 支持哪些镜像、入口命令、输入输出格式和最大文件大小？
4. 是否完全关闭 Jupyter/SSH；若开放，安全负责人是否批准独立的交互模式？
5. 任务允许哪些网络出口，是否需要域名白名单和人工审核？
6. 输入、输出、日志和临时卷各自保留多长时间，删除失败如何处理？
7. 个人卖家设备故障时的退款、赔付和信誉扣分规则是什么？
8. 哪些指标达到上线门槛后，才允许扩大设备矩阵、开放自定义镜像或引入 Kubernetes？

## 9. 第一版开发顺序总结

开发顺序固定为：

1. 契约、威胁模型、权限矩阵和数据生命周期。
2. 身份、角色、审计、节点注册和心跳。
3. Listing、价格快照、资源锁、支付沙箱和订单状态机。
4. 受限 sandbox、GPU 绑定、capability token 和清理。
5. Job API、Gateway、artifact 和网络出口策略。
6. 计量、退款、账本、结算、争议和对账。
7. 运营台、告警、备份、攻击型测试和受邀试运行。

第一版的验收核心不是“买家能否打开一个远程终端”，而是：**买家能否在付费租约内稳定完成指定 GPU 任务，同时无法看到、修改或持续占用卖家的主机、磁盘、网络和其他租约资源。**
